# Sandbox Filesystem And Executable Preparation

`agora-sandbox` provides a rootless, process-tree-scoped filesystem view on macOS. Supported path operations read through to the host filesystem, while sandbox mutations use a persistent copy-on-write tree. The original host paths are never modified except for roots deliberately listed in the compile-time native-passthrough allowlist; that list currently contains only `/dev` so device operations retain kernel semantics.

The filesystem and network views are cooperative boundaries, not a kernel namespace, and apply only to processes that load the Agora hook library. Executable preparation fails closed when a process cannot be made injectable. The runner does not install a native macOS process sandbox or virtualize Keychain APIs; descendants use the current user's host Keychain directly.

## Storage Layout

`SandboxConfig::new` defaults the work directory to `~/.agora-sandbox`. The CLI reads optional `workdir` from the `run` configuration and uses the same default when it is omitted; the SDK exposes `SandboxConfig::with_workdir`.

`<workdir>/fs` is the only persistent filesystem backing tree. Absolute logical paths are mirrored below it: `/usr/bin/curl` maps to `<workdir>/fs/usr/bin/curl`. There is no disk image, mount point, or separate `filesystem` directory.

Control data is stored in place:

```text
<workdir>/fs/
├── .fs.lock
├── .key.json              # encrypted mode only
├── .metadata              # managed-directory root marker
├── .vfs.lock
├── .rekey.json            # only while key migration is recoverable
├── usr/
│   └── bin/
│       └── .metadata
└── ...
```

Every physical upper directory, including merge-only directories, contains one valid `.metadata` marker. The marker chain from `<workdir>/fs/.metadata` to an upper object is continuous; an empty version-3 marker is valid and does not make the directory authoritative over lower. Hidden `.agora-write-lease-*` sidecars track writable encrypted entries and protect in-flight plain-file publication. Hooked processes cannot access the physical work directory or any physical control path, even when they know the absolute path. Directory enumeration hides control entries. A sandbox may still create a logical business file with a reserved control name such as `.metadata`, `.fs.lock`, `.key.json`, `.vfs.lock`, or `.rekey.json`; exact names, dot-suffixed variants, and internal backing-name prefixes use an encoded physical filename and remain separate from control data.

Automatically managed TLS CA certificate, key, and trust-bundle files remain under `<workdir>/ca`. The CLI materializes its embedded, linker-signed hook before sandbox startup at `<workdir>/runtime/hook/<md5>/libagora_sandbox.dylib`, using `<workdir>/runtime/hook/.lock` to serialize publication. The lowercase MD5 covers the complete dylib and matching regular-file content is reused without rewriting it. A same-user regular file with the wrong size, unreadable content, or a mismatched checksum is atomically replaced from the embedded bytes; foreign-owned files remain an error. This controller-owned runtime cache is outside `<workdir>/fs`: it has no overlay metadata, filename or content encryption, lower-layer fallback, or filesystem audit representation. Prepared SIP-restricted executables are persistent plaintext cache entries at their mirrored paths below `<workdir>/fs`; for example, `/usr/bin/curl` is cached at `<workdir>/fs/usr/bin/curl`. They are controller-managed executable artifacts rather than encrypted business COW files and are reused only while the recorded source identity and target platform/architecture variant match and the cached file's MD5 still matches its record.

## Storage Modes

The CLI treats its JSON configuration path as caller-managed input and does not enforce file ownership or permission bits. `filesystem.local.encrypt: "plain"` in that configuration selects the persistent `<workdir>/fs` tree without file-content encryption and rejects `filesystem.local.key`. Plain mode is the CLI and SDK default when the setting is omitted.

`filesystem.local.encrypt: "encrypted"` with a non-empty `filesystem.local.key`, or `SandboxConfig::with_encrypted_workspace`, selects encrypted mode. The non-empty check is structural, not a strength guarantee: operators must provide a high-entropy secret because a short or human-memorable value permits offline guessing by anyone who obtains the ciphertext tree. The first run creates `<workdir>/fs/.key.json` with a random salt and derived key identifier. Later runs derive the cipher again and reject a different key before starting the child. Existing unmanaged data is not imported into encrypted mode.

Encrypted regular files use content format version 2. Each container has two authenticated generation headers carrying a random file ID and logical length, followed by independently authenticated 4096-byte AES-256-GCM blocks. A per-file key is derived from the runtime cipher key and file ID with HKDF; each written block receives a fresh nonce and authenticates its file ID and block index. Absent or all-zero physical block slots represent sparse logical zeroes, so allocated block contents are authenticated but the sparse allocation map itself is not: removing or zeroing an entire slot can turn that block into a sparse zero. Content format version 1 is not supported, and encrypted deployments must start with a fresh `<workdir>/fs`.

The controller derives the runtime cipher key with PBKDF2-HMAC-SHA256 and 100,000 iterations once per sandbox startup; injected descendants receive only the derived 32-byte key, so each exec does not repeat PBKDF2 or inherit the passphrase and salt as runtime configuration. Version 1 of `.key.json` implies those KDF parameters. Its version field is the compatibility and migration boundary for any future KDF change; an existing workspace must never silently switch parameters. Directory paths remain mirrored. For each encrypted business file or symlink, the original logical leaf bytes are authenticated-encrypted with AES-256-GCM under a filename-specific domain and encoded as an `enc_` URL-safe token. That ciphertext token is both the physical leaf name and the parent `.metadata` record key; there is no independently generated random alias, `backing_names` map, or separately persisted logical-name field. Filename encryption uses a fresh nonce, so recreating the same logical name may produce a different ciphertext token without introducing an unrelated backing name. Plain-mode entries and controller-managed executable caches retain literal logical names, with reserved prefixes escaped losslessly. Physical business files beneath `<workdir>/fs` remain ciphertext while the sandbox is running. Lower files without an authoritative upper entry are opened directly from their host paths.

Encrypted upper opens use one anonymous, unlinked plaintext vnode per ciphertext backing inode. A separate authenticated local-filesystem Broker in the parent owns that vnode and the open ciphertext container; it is independent of the NFS Broker and starts only in encrypted mode. Every independent logical open receives a duplicate of the shared plaintext vnode, a separate anonymous state descriptor containing its logical offset and status flags, and a separately opened descriptor for one shared per-inode lock anchor. Descriptor duplicates and fork descendants share the original open state, while a later independent open receives new state. The hook implements `read`, `pread`, `readv`, `write`, `pwrite`, `writev`, and `lseek` against that state with positioned native I/O, so the kernel offset shared by duplicated vnode descriptors is never application-visible. The state descriptor combines a process mutex with a cross-process record lock, preserving offset and flag ordering after `fork`. The lock anchor gives independent opens the same `fcntl` and `flock` locking identity without exposing a plaintext path. The shared vnode makes completed writes and shared mappings immediately visible to every open and avoids repeated decryption or peer-snapshot copying.

Successful intercepted writes and truncation reserve their mutation with the Broker before native plaintext mutation and report the completed byte range immediately. The Broker serializes mutation ownership per backing inode, reserves the current shared EOF for append, and may merge completed ranges for at most ten milliseconds before updating only the affected ciphertext blocks and logical length. Completing or cancelling one token never clears another token. The last Broker reference treats an abandoned active reservation as potentially dirty before releasing the handle, preventing a lost finish notification from permanently excluding changed bytes. Every Broker request carries a random request ID; ambiguous transport failures retry the same ID, and the Broker waits for an in-progress duplicate or replays its bounded 120-second result. An open response must be claimed, and an unclaimed response is aborted on expiry instead of leaking descriptors. Fork retains are acquired in the parent before native `fork`, inherited by the child without a post-fork Broker call, and atomically released if fork fails; closed retention handles remain briefly replayable and are bounded by age and count. Existing containers retain their physical inode during block updates and truncation, while namespace creation uses the overlay's lock-serialized publication flow. Direct host reads of upper storage therefore see only ciphertext, while hooked processes share one coherent plaintext vnode.

The root `.fs.lock` gives one runtime exclusive ownership of a work directory and excludes key migration. The SDK's `Sandbox::run` owns it for one command. Overlapping CLI `run` invocations with the same canonical workdir, build, and effective configuration instead join one ephemeral per-workspace session daemon, which holds the lock and shared controllers until the final command releases its lease. A mode-0600 startup lock at `<workdir>/runtime/session-start.lock` elects that daemon and remains inherited for its lifetime; the owner-only session socket uses a short SHA-256-derived name below `/tmp/agora-sandbox-session-<uid>`. Different effective configuration or build identities are rejected rather than sharing runtime credentials. `.vfs.lock` serializes short overlay metadata and publication transactions across every process in that runtime. A fork-aware per-process pool reuses unlocked descriptors for sequential transactions, opens distinct descriptors for overlapping transactions so advisory locking still serializes threads, and discards inherited pooled descriptors after a PID change. The same file stores an eight-byte metadata publication generation. Per-process metadata caches compare that generation while holding the VFS lock, including cached absence, so a publication by another sandbox process invalidates stale directory state without reopening every `.metadata` file. Cached directories also retain the physical marker identity; a marker removed or replaced outside the sandbox invalidates the local cache and advances the shared generation. Batched record lookup deduplicates the requested ancestor closure and reconciles each reachable path once. When an ancestor has no reachable upper directory and marker, deeper upper records are untrusted and skipped; an encountered whiteout still rejects requested descendants. Validation remains lazy and startup does not recursively scan the upper tree. A writable encrypted backing identity holds a shared namespace lease that records its currently attached ciphertext destination. Writers do not block one another at the namespace layer; content mutations are ordered by the Broker. Regular-file rename moves and retargets the source lease so its open handles continue writing to the renamed path; handles for a replaced target become detached. Unlink removes the current lease sidecar and detaches existing handles, whose later writeback is ignored instead of recreating the name. Directory rename still takes non-blocking exclusive leases for affected subtrees and returns `EBUSY` while an affected writable handle remains attached. Different work directories are independent.

## Copy-On-Write View

The VFS owns path normalization, physical-name encoding, lower-layer reads, whole-file copy-up, whiteouts, per-directory metadata, encryption, lock-serialized publication, and logical owner/group/other authorization. Each authorized VFS operation resolves paths, checks the operation-specific permissions, and stages or applies its namespace change through one scoped overlay transaction and one `.vfs.lock` snapshot. Within that transaction, final-follow operations reuse the resolved logical endpoint for attribute checks, and ancestor search returns the immediate parent's effective attributes for a later parent write check; neither endpoint nor parent is resolved a second time. The hook is an adapter for libc operations, credential selection, descriptor tracking, and audit events; it does not calculate overlay or mode-bit policy or pre-authorize a later VFS mutation. Open remains two-phase: authorization and staging share the first transaction, a per-file lease protects the staged backing while native descriptor construction occurs without the namespace lock, and a short second transaction publishes `cow` only after descriptor construction succeeds. In plain mode that lease is released after publication; in encrypted mode it remains attached to the shared Broker vnode. Reconciliation does not discard an unrecorded upper object while its staging lease is active, so another concurrently entered CLI process cannot treat a just-created upper file as an external artifact. Failure still drops the staged state without publishing metadata.

Reads prefer an authoritative `cow` upper entry and reject a `whiteout`. Otherwise a lower file or directory is opened directly from its host path without copying it, creating upper directories or metadata, or passing it through decryption. Read-only regular opens and stat-family calls use the native host operation directly when the requested path, its resolved symlink target, and their ancestor chains have no overlay entry-state override. A logical-attribute override on the endpoint still requires full VFS metadata patching; an allowed ancestor attribute override does not disable the native metadata fast path after its execute/search permission has been checked, while a denied ancestor does. Mutating and special-flag operations continue through the full VFS path. A `cached` entry is non-authoritative and is reserved for explicit materialization such as executable preparation or a staged mutation; normal reads continue to use lower until the mutation commits as `cow`. A later staged write refreshes stale cached data when the lower checksum changes. Source-derived cached attributes refresh with that lower snapshot, while an explicit logical attribute override remains authoritative across copy-up and a failed native open. Cached lower MD5 values used by ordinary copy materialization and prepared executable validation are change detectors, not security primitives.

A successful write-intent open changes an entry to `cow`. Existing lower data is copied up first; newly created data exists only in the upper tree. An encrypted `O_CREAT|O_EXCL` open reserves the logical leaf's encrypted ciphertext token while holding `.vfs.lock`, so another VFS cannot create the same logical path before the first open commits; abandoning the staged open removes the reservation. Permission failures are rejected before copy-up; a later native open failure leaves any staged cache entry non-authoritative. COW entries are never refreshed from the lower path.

Before using upper state, the VFS reconciles it while holding `.vfs.lock`. A `cow` or `cached` record whose physical backing object was removed outside the sandbox is deleted together with its logical attributes, encrypted-name reservation, and attached write lease, after which lookup falls through to lower. A `whiteout` remains authoritative when no backing object exists; an unexpected object at a whiteout path is removed without clearing the whiteout. An attribute-only lower override remains valid without upper data. An unrecorded upper file or symlink is removed, and a physical directory without its own marker is removed recursively even when a descendant marker looks valid. Removing a whole upper directory outside the sandbox therefore makes the next access use lower in the same running process. Before any intercepted spawn or exec, an invalid native cwd is re-resolved from the tracked logical cwd through the same reconciled view and moved to its current NFS, upper, or lower representation. If that logical directory no longer exists or cannot be authorized, child creation fails closed instead of inheriting an unlinked cwd and resolving later relative paths outside the managed view. Cleanup failure aborts the operation instead of exposing a partially reconciled view, while invalid JSON in an otherwise continuous marker chain remains a hard error.

Deletion records a `whiteout`, hiding any lower entry with the same logical path. Unlink and rmdir publish that authoritative whiteout directly in one parent metadata publication and then remove upper data and a regular-file write lease idempotently. Rename validates POSIX type, descendant, non-empty-directory, and materializable-file constraints before copy-up, preserves ordinary symlinks when materializing a lower directory, and then directly renames upper state while holding `.vfs.lock`. It retargets a regular-file write lease and updates logical metadata after the physical rename. Source whiteout and destination `cow` are published together when both names share a parent, while cross-directory rename publishes one marker per parent. Case-only rename compares exact directory-entry spelling in addition to inode identity, and renaming between hard links to the same inode is a no-op. Namespace operations do not maintain a journal, backup, rollback transaction, or abnormal-exit/power-loss recovery guarantee; a process or storage failure between their physical and metadata steps may leave state that must be reset by deleting the affected upper workspace outside a running sandbox. Special files that would require copy-up fail without leaving staged upper data. Before VFS lookup, the hook normalizes logical absolute paths and checks the compile-time `NATIVE_PASSTHROUGH_ROOTS` list. `/dev` and its descendants currently bypass COW lookup, metadata overrides, backing-path rewriting, encryption, descriptor/directory tracking, and filesystem audit for every covered path- or descriptor-based filesystem operation; component matching excludes `/developer`, and normalization prevents `/dev/..` escapes. Relative `*at` paths are classified only after resolving their directory descriptor. Native kernel permissions and errors are authoritative on that branch, and write opens such as `/dev/null` never create COW metadata. Operations with two filesystem operands delegate to native libc only when both operands resolve inside the allowlist; a rename crossing the allowlist boundary fails with `EXDEV`, while unsupported link/clone/copy families retain `ENOTSUP`, so an allowlisted operand cannot expose another host path. Intercepted non-allowlisted `opendir`/`fdopendir` plus `readdir`/`readdir_r` enumeration merges NFS, upper, and lower names when an NFS route applies, otherwise upper and lower names only. It prefers NFS over upper and upper over lower, filters overlay whiteouts from the overlay portion, decrypts encrypted logical names, and hides controls. During managed macOS FTS traversal, interposed `getattrlistbulk` synthesizes that same merged view so system tools receive NFS and upper-only files as well as lower entries; `fts_children` and `fts_read` additionally filter whiteouts, repair synthetic metadata where libc reports `FTS_NS`, patch encrypted-file stat records with plaintext sizes and logical attributes, and present logical paths and names instead of backing paths. Native caller comparators receive temporary entries containing those logical paths and names, never ciphertext backing names. `rewinddir` rewinds every contributing stream and resets merged-view deduplication. `fdopendir` retains the descriptor's actual layer when the view changes after `open`; it opens any complementary layers before transferring descriptor ownership, so preparation failure leaves the caller's descriptor open.

Each directory's `.metadata` is versioned JSON. Version 3 has one `entries` record map; each record may contain entry state and logical attributes. For encrypted business files and symlinks, the authenticated filename ciphertext is the record key and the physical leaf name, so neither plaintext logical names nor `backing_names` or `name` fields are persisted. Plain-mode entries and controller-managed cached executables use literal UTF-8 record keys; non-UTF-8 bytes and names beginning with reserved `base64:` or `enc_` prefixes use `base64:<URL_SAFE_NO_PAD>`. The decoder can still read versions 1 and 2 when directly encountered, but normal startup neither recursively scans nor rewrites legacy metadata and compatibility is not guaranteed; deployments must start this format with a fresh `<workdir>/fs`. Entries are `cached`, `cow`, or `whiteout`; non-authoritative cached entries carry a materializer type and source identity. Ordinary copy materialization additionally carries a lower MD5, while executable materialization carries the prepared output MD5 and target platform/architecture variant. Logical mode, owner, group, and access/modification times are stored in the same record and remain separate from physical ciphertext attributes. A directory marker is limited to 64 MiB, 100,000 records, and 4096 bytes per stored record name. Encrypted write-lease destinations are limited to 16 KiB. `.key.json` is limited to 64 KiB; `.rekey.json` is limited to 64 MiB, 100,000 entries, and 16 KiB per encoded path. Readers enforce the byte limit before allocation and again while reading, so concurrent growth cannot create an unbounded allocation. While holding `.vfs.lock`, general metadata updates truncate and rewrite the existing marker inode; a new whiteout record uses a validated append fast path and one cached descriptor so recursive deletion does not repeatedly serialize, reopen, or replace the growing marker. Every successful update advances the generation stored in `.vfs.lock` and updates the process-local cache. Metadata updates deliberately do not use a temporary file, journal, file sync, or parent-directory sync and therefore guarantee visibility to running processes, not persistence across abrupt process termination or power loss. Ciphertext and key-migration publication retain their separately documented synchronization behavior.

## NFS Roots

The source module named `nfs` owns protocol-backed filesystem roots; the name describes Agora's generic network-filesystem layer and does not require the NFS wire protocol. `nfs/backend/mod.rs` defines the protocol-neutral backend trait and error boundary, while protocol-specific implementations live in private child modules. SMB2/3 is the first implementation and lives in `nfs/backend/smb/`; its storage type, sessions, path mapping, and protocol error adaptation are not visible outside that module. The existing `SmbRemoteConfig` public API is defined there and re-exported through `nfs` and `runner` without exposing the implementation module. The generic Broker and controller depend only on the storage trait. Later protocols must implement the same storage boundary instead of adding protocol logic to the hook or leaking implementation types into the generic NFS layer.

The CLI reads remote roots from the unified run configuration's `filesystem.nfs` array. An SMB
entry has `type: "smb"`, a logical `dir`, a `server` URI, and optional `username` and `password`.
The URI grammar is `smb://host[:port]/share[/remote/path]`; credentials in the URI, query strings,
and fragments are rejected. IPv6 literal endpoints, bracketed or unbracketed and with or without an
explicit port, are rejected because the current SMB backend cannot construct a valid TREE_CONNECT
service name for them; hostnames remain accepted even when DNS may resolve them to IPv6. The SDK
equivalent remains `SandboxConfig::with_smb_remote`, whose
typed configuration also supports an SMB domain. Logical roots must be normalized absolute
non-root paths and may not overlap another NFS root, `/dev`, or any part of `<workdir>`; validation
also compares existing canonical ancestors so a symlink alias cannot bypass those boundaries.

```json
{
  "tls": "off",
  "filesystem": {
    "local": { "encrypt": "plain" },
    "nfs": [
      {
        "type": "smb",
        "dir": "/network/team",
        "server": "smb://files.example.com/documents/projects/current",
        "username": "alice",
        "password": "secret"
      }
    ]
  }
}
```

An NFS root contributes the highest-priority namespace layer, so lookup order is `NFS > upper > lower`. An existing NFS entry wins over an upper entry, overlay whiteout, or lower entry with the same logical name. An NFS `ENOENT` falls through to the normal overlay lookup; any other NFS error fails the operation instead of silently exposing another layer. Directory enumeration merges all available layers and emits each logical name once with the same priority. Each configured root is also injected as a synthetic directory entry into its existing logical parent for both ordinary and managed FTS enumeration, without creating a host or upper placeholder; it hides a same-named local entry and remains visible while its backend is unavailable, while access still reports the backend error. Removing an NFS entry therefore reveals an existing upper/lower entry immediately, while removing a path absent from NFS applies normal overlay deletion. Existing fallback entries retain normal COW and encryption behavior. A create under an NFS route uses an existing visible upper/lower entry when one exists, but a path absent from every layer is created directly in NFS.

Remote objects themselves bypass COW storage, filename/content encryption, whiteouts, and `.metadata`. The runner does not mount the share in the host namespace. Instead, a per-run parent-process Broker owns credentials and one backend session holder per configured root. After the Broker is ready, its controller starts one independent connection probe per root without awaiting those probes before spawning the child. The logical root leaf is synthetic, but its parent must already be visible as a directory in the local overlay when the probe starts; otherwise the route reports `ENOENT` or `ENOTDIR` without attempting an SMB connection. For an SMB share URL with a configured subpath, the probe also stats that subpath and reports success only when it exists as a directory; a pure share root needs only a successful share connection. A successful probe retains the established backend session; a failed probe leaves the holder available for a later filesystem access to retry normally. Each completed probe becomes a controller status event, and the runner writes one sanitized structured `nfs` log record containing the route, status, logical root, endpoint, and failure errno when applicable, but no username or password. The record uses the same logger and destination as CLI audit records and never enters child stdout. Probe failure neither terminates the Broker nor the child. Every `filesystem.nfs` array entry receives a stable route index, so one run can expose multiple independent SMB roots. The injected hook receives only normalized logical routes plus a per-run authenticated Unix socket; endpoint, share, username, domain, and password never enter the child configuration. Remote protocol version 7 supports authenticated persistent control streams, direct positioned range I/O, append-at-current-EOF writes, resize, range-aware snapshot materialization, and dirty-range synchronization. An authenticated `ping` converts one connection into the inheritable multi-request fallback used when a nested kernel sandbox denies a new Unix connection. The socket, opaque empty metadata anchors, and unlinked payload or snapshot files live in a mode-protected short temporary directory under `/tmp` and are removed with the run. Named anchors contain neither a remote name nor file content. Stat and list responses create fresh anchors rather than caching one per remote path; the hook owns each claimed anchor through a short RAII lifetime, and unclaimed response resources expire from the Broker cache. NFS opens and closes still use the normal filesystem audit channel.

A regular-file open retains one backend file handle and returns a correctly sized sparse anonymous descriptor without downloading file content. Interposed scalar and vector `read`, `write`, `pread`, and `pwrite` operations transfer at most 64 KiB per syscall request through unlinked descriptor payloads; content is never embedded in the JSON control frame. Reads fetch the requested remote range, and successful writes reach the persistent backend handle before the syscall returns. `O_SYNC` and `O_DSYNC` direct writes additionally issue backend FLUSH before returning; after a handle transitions to snapshot mode, the same flags publish the changed snapshot before a successful scalar or vector write returns. `fsync`, full-sync `fcntl`, pre-exec flush, and last tracked close issue backend FLUSH rather than downloading or replacing a direct-mode file. `ftruncate` and path truncate resize the persistent handle directly. Within one process, descriptor aliases share one tracked registration and the native anonymous descriptor's open-file offset; the registration lock orders sequential `read`/`write` and append calls, while `pread`/`pwrite` leave that offset unchanged and ordinary `lseek` remains native. Append uses the descriptor's current status flags, including changes made through `F_SETFL`, and refreshes the server-reported length while holding the Broker's per-root mutation lock; an external SMB client that ignores that cooperative ordering can still race the length query and write. Each write payload carries its length and MD5 in the idempotent request fingerprint. MD5 detects a mismatched or changed retry payload and is not a cryptographic integrity boundary. Existing-file `O_TRUNC` is deferred until the normal open audit succeeds. A failed pre-registration create is removed only when the backend CREATE response proves that this open created it and the path still has the same identity, so an external racing create is not deleted.

Operations that require the kernel to access file data without a later intercepted scalar/vector call transition the open handle from direct mode to a sparse anonymous snapshot. `mmap`, `aio_read`, and `lio_listio` reads materialize only their declared file ranges; mmap uses the exact mapping range, while later scalar and vector snapshot reads share the local encrypted path's adaptive 16-256 KiB read-ahead policy. The Hook and Broker use the same byte-range set implementation to cache successful local and remote materialization and avoid downloading overlapping ranges twice. The persistent backend handle remains open while the snapshot is partial. Ambiguous operations such as `sendfile` with headers, `fcopyfile`, guarded or asynchronous writes, `SEEK_DATA`, and `SEEK_HOLE` materialize the missing remainder before native access. `MAP_PRIVATE` modifications never write back, and a clean partial snapshot closes without downloading its unobserved ranges.

Writable `MAP_SHARED` mappings and native snapshot writes report their completed byte ranges at `msync`, mapping teardown, descriptor sync, pre-exec flush, or last close. Those ranges are already valid local plaintext and are never overwritten by deferred remote reads. Before publishing a changed snapshot, the Broker downloads only still-missing bytes from the opened baseline up to the resulting logical length, closes the persistent backend handle, computes MD5 with a fixed-size buffer, and uses whole-file optimistic CAS. Truncation is detected from the anonymous descriptor length. A snapshot that was fully materialized before native access retains checksum-based fallback detection for interfaces whose completed range cannot be observed precisely. The SMB backend streams range downloads and snapshot uploads in fixed-size chunks instead of constructing a whole-file `Vec`; clean read-only or private mappings therefore use staging space and network transfer proportional to the accessed ranges, while changed snapshots still require a complete local baseline and whole-file upload. It queries the opened object's identity before and after each deferred range transfer and rejects a changed object with `ESTALE` rather than exposing mixed-version contents; impossible advertised lengths, premature EOF or empty responses, and responses larger than the requested or remaining range fail as protocol errors. Writeback acquires a deterministic cooperative sibling lock, creates an opaque randomly named sibling, writes its complete contents, sets its length, flushes and closes it, then opens the current target and verifies its baseline identity. A mismatch returns `ESTALE`; otherwise one SMB rename atomically publishes the staged file. The cooperative lock provides strong CAS between Agora writers; external clients that ignore that lock can still replace the target between verification and publication, so their detection remains best effort. Failures attempt to remove the staged sibling, and a transport ambiguity drops and reconnects the backend session before retrying the same staged operation; the original target is never left partially overwritten. An unreachable share or process crash can still leave an opaque staging or lock file for external cleanup. Only exact `.agora-write-<32 lowercase hex>.tmp` and `.agora-lock-<32 lowercase hex>.lck` leaf names are reserved: directory listing hides them and direct public storage operations reject them, while similarly prefixed business names remain visible and accessible. Ordinary SMB rename retains replace-if-exists semantics for both files and directories and reconnects before resolving an ambiguous transport result from observed namespace state. Rename detaches a replaced destination handle before retargeting open source descendants. Unlink detaches matching open handles, and later sync or close does not recreate the removed path.

Selected NFS directories use synthetic logical views backed by opaque empty anchors for `stat`, `opendir`/`fdopendir`, `readdir`, relative `*at` operations, current-directory operations, and managed FTS traversal; overlay directory streams are attached to that view when fallback layers also exist. A successful remote `chdir` keeps the native process cwd on its opaque anchor and tracks the logical NFS path. Intercepted `posix_spawn` and `exec` calls replace any caller-provided remote-cwd variable with that tracked path. A new hook runtime restores it only when the inherited native cwd is a valid anchor beneath the configured Broker runtime and the logical path still belongs to a configured route, so external commands launched after `cd` retain the same logical directory without exposing the runtime path. `mkdir` creates in NFS only when the name is absent from every layer. Unlink/rmdir removes the selected NFS object first and otherwise delegates to overlay deletion. A rename whose source is selected from NFS is sent to the backend; a source selected from upper/lower remains an overlay rename when both operands stay in the same NFS route and no NFS destination shadows it. A rename crossing NFS roots or crossing between an NFS route and host/COW paths returns `EXDEV`; the configured root itself cannot be removed or renamed. Regular NFS files are presented as non-executable mode `0666`, directories as `0777`, and owner/group as the effective process identity; regular-file `X_OK` fails. Symlink, hard-link, ownership, mode, timestamp, flags, xattr, clone, and copy mutations are not currently represented by the backend trait and return `ENOTSUP` for a selected NFS object rather than mutating a same-named fallback object.

Content-mutating `fcntl` commands on a direct or snapshot remote descriptor return `ENOTSUP` instead of mutating only its anonymous local placeholder.

This is a hybrid userspace client, not a mounted kernel shared-inode implementation. Direct handles expose backend range I/O and write-through visibility; snapshot handles retain whole-file optimistic coherence, so two changed snapshots of the same baseline conflict after the first publication and an unchanged snapshot never overwrites newer remote data. Every request carries a random request ID. The hook retries an ambiguous transport failure with the same ID, while the Broker executes the operation once, waits for an in-progress duplicate, or replays the completed response. Resource-bearing open, read, stat, and list responses require a follow-up claim; unclaimed handles, payloads, anchors, and list descriptors are reclaimed when the bounded response cache expires. Directory entries flow incrementally from bounded SMB query pages into an anonymous descriptor and are decoded with an independent positioned cursor, so no SMB page, generic Broker collection, or control frame must contain the full directory. A list is rejected with `EOVERFLOW` above 100,000 visible entries or a 64 MiB serialized payload; the hook checks both descriptor length and entry count before later validation allocations. A named anchor remains opaque but is padded to at least the logical basename byte length so Darwin FTS can substitute a longer logical name safely. A claimed list anchor is owned by an RAII guard before descriptor parsing, so malformed or oversized payloads remove it immediately. Close and abort retain bounded tombstones so retrying either operation is idempotent. A background connection-probe failure is informational; a backend/network failure during a covered filesystem operation fails that operation, and a Broker service failure terminates the run. The 8 GiB limit applies only when an operation requires whole-file snapshot materialization; larger files remain available to ordinary direct range I/O. The Broker gives each request one absolute 15-minute execution deadline across backend calls and checksum work, then attempts backend-session reset for at most five seconds and returns `ETIMEDOUT`; hook requests wait 15 minutes and five seconds per transport attempt. The controller separately bounds an incomplete initial request to one second and a blocked response to five seconds, while transport writes suppress `SIGPIPE`. Unsynchronized changes can still be lost on fatal termination, and sharing an inherited NFS descriptor between processes that continue after a non-exec `fork` remains outside the supported lifetime/coherence model.

## Hook Semantics

At the local filesystem Broker protocol boundary, acquiring a busy shared plaintext inode never
waits while an inherited control-stream lock is held. The Broker returns `EAGAIN`, and the client
releases that stream lock before a bounded retry with a fresh request ID and the same logical write
ID. Completed dirty ranges belong to the shared plaintext inode rather than an individual open
handle, so synchronization through any handle flushes all completed writes for that vnode.

The compile-time `platform` facade selects the private platform hook implementation; it has no runtime dispatch or cross-platform hook trait. The current implementation lives under `platform/macos/hook`. Its `mod.rs` owns the dylib initializer, global initialized state, config/control/filesystem startup, filesystem exit-flush registration, and the generic errno setter shared by child domains. `control.rs` owns the workload-independent inherited execution, audit, local Broker, and remote Broker streams; crate-level `ipc` supplies their anonymous descriptor lock and per-stream thread serialization. `abi.rs` owns Darwin ABI declarations and architecture-specific symbol bindings, including the `$INODE64` FTS variants used on x86_64 and the distinct canonical and cancellation-safe `close` entry points. `filesystem/mod.rs` owns the filesystem facade, shared runtime, guards, path/audit adaptation, descriptor identity, and preparation flows reused across libc operation families; its operation modules and C variadic shim are colocated under `filesystem/`. `open.rs`, `descriptor.rs`, `metadata.rs`, `namespace.rs`, and `unsupported.rs` own the original operation families; `data.rs`, `mapping.rs`, and `lifecycle.rs` own plaintext data I/O and write reporting, mapped-memory lifecycle, and fork retention. `nfs.rs` adapts logical NFS roots to the authenticated remote Broker without containing backend protocol logic. Directory enumeration and current-directory operations live in `filesystem/directory/mod.rs`; Darwin FTS and virtual `getattrlistbulk` support live in its nested `fts.rs`. Parent-side encrypted content synchronization lives under the crate-level `filesystem/broker`, independently of the generic remote backend and Broker under `nfs`; both use the crate-private descriptor-capable framing in `ipc`. The platform hook's `network/mod.rs` owns `connect`/`connectx` interception and network recursion/runtime state, with raw socket conversion in `network/socket.rs` and Security.framework trust interception in `network/trust/mod.rs`. Process execution interception and its tests live under `process/`. Narrow implementation dependencies are limited to native cleanup, logical stat patching for FTS, and the shared runtime's native `/dev` namespace helpers; operation policy remains in the VFS, local encrypted Broker, or NFS Broker.

The hook covers `open`, `openat`, `creat`, `fopen`, `stat`, `lstat`, `fstat`, `fstatat`, `access`, `faccessat`, `readlink`, `readlinkat`, `realpath`, `symlink`, `symlinkat`, truncate, deletion, ordinary rename, zero-flag `renamex_np`/`renameatx_np`, directory creation, current-directory operations, `opendir`/`fdopendir`/`readdir`/`readdir_r`/`rewinddir` enumeration, macOS `fts_open`/`fts_children`/`fts_read`/`fts_close` traversal and its `getattrlistbulk` enumeration, `write`/`pwrite`/`writev`/`pwritev` including Darwin non-cancel variants, `aio_read`/`aio_write`/`lio_listio`, `mmap`/`msync`/`munmap`/`mprotect`, `fork`, `close`, `fclose`, `fsync`, `dup`, `dup2`, and relevant `fcntl` operations. Before entering the generic Rust filesystem guard, the mapped-memory interposers classify requests through an atomically published mapping-range snapshot and a fixed-size tracked-descriptor bitmap rather than locking the authoritative mapping or descriptor tables. Requests proven not to reference tracked state delegate directly to libc; descriptors outside the bitmap's range conservatively enter the managed path and consult the authoritative table. Managed operations acquire one nonblocking per-runtime mapping transaction, reclassify while holding it, and keep the kernel operation and corresponding mapping-state change in that transaction. Descriptor-table publication participates in the same transaction. An unavailable configured runtime or contended managed transaction returns `EAGAIN` without executing the native operation. This keeps allocator and dyld memory management out of the logical filesystem state machine without turning uncertain requests into a policy bypass. Native routing before the hook initializer completes is bootstrap behavior only; a configured initialization failure still terminates the child with status 126. The macOS `removefile` and `removefileat` APIs are also interposed but fail closed for managed paths because their secure-erasure semantics cannot be represented by the overlay. Relative `*at` operations resolve tracked directory descriptors through logical paths, including duplicated descriptors; successful close removes directory tracking immediately, while encrypted file state remains tracked until its last descriptor and mapping reference is gone. `realpath` resolves visible upper and lower components and symlinks but returns only the canonical logical path; both caller-provided buffers and libc-allocated null-buffer form are supported. Directory creation checks searchability and an already-visible endpoint before parent mutation permissions, so BSD `mkdir -p` receives `EEXIST` for an existing prefix. `fchdir` resolves the descriptor's logical path before changing the native current directory and fails closed when that resolution is unavailable. Successful local `chdir` and `fchdir` calls resynchronize the tracked path from the native current directory, translating a prepared upper directory back to its logical path and collapsing host aliases such as `/tmp` and `/private/tmp`; remote directory changes retain the logical NFS path and propagate it through the protected child runtime environment described above. Managed FTS streams force `FTS_NOCHDIR`, map prepared upper roots to logical presentation paths, and therefore do not perform per-entry current-directory resynchronization; untracked native FTS streams retain the defensive resynchronization path.

Encrypted upper regular-file descriptors refer to a shared anonymous plaintext vnode; direct lower reads retain native host descriptors. Each independent encrypted open virtualizes the caller's requested access mode, append/nonblocking flags, and logical offset in its separate state descriptor. `dup`, `fork`, and exec inheritance retain that open-description state, while later independent opens do not share it. On macOS, guarded open, write, positional write, vector write, and close operations retain the caller's descriptor guard and pass through the same tracking and synchronization path as their ordinary counterparts. Broker-backed local plaintext descriptors start close-on-exec, but explicit `F_SETFD`, `dup`, `dup2`, and `F_DUPFD` operations retain native inheritance semantics so shell redirection can pass a descriptor to an external command; `F_DUPFD_CLOEXEC` remains close-on-exec. Before exec, the hook places only inheritable local content, state, lock, and Broker-handle records plus authenticated internal control descriptors in the protected child runtime environment. The control descriptors stay open across exec and share one unlinked anonymous control-lock file; a process-local mutex serializes threads and independent byte-range record locks serialize descendant processes without coupling different services. A fresh control bundle authenticates every service before startup. A complete inherited bundle instead validates descriptor completeness, uniqueness, type, and peer identity, then reuses the already-authenticated streams without redundant `ping` round trips; every real protocol request still carries its service token, and a transport failure reconnects through the fully authenticated fresh path or fails closed. Executable preparation preferentially reuses its inherited multi-request stream rather than opening a TCP connection per request. The new image validates the physical identities of inherited content and per-inode lock descriptors, restores the per-open state and shared local Broker handle, and separately restores the encrypted backing identity reported to the application. Local Broker protocol version 8 uses an authenticated `ping` to establish a fresh multi-request stream. After a PID change, service clients prefer the inherited stream for the first transaction; if that descriptor is invalid, the idempotent retry attempts a fresh authenticated connection instead of resetting the same stale preference on every attempt. Anonymous remote data descriptors and local data descriptors without Broker support remain forced close-on-exec, and `F_SETFD` cannot clear that bit. Descriptor duplicates and writable `MAP_SHARED` mappings share one local Broker handle. Closing the last descriptor does not release that handle while a mapping remains, and a fork retains inherited local Broker handles in the child. `MAP_PRIVATE` mappings are never written back. Writable shared mappings register their complete file ranges before they can be modified; `msync`, `munmap`, removal of write permission, `MAP_FIXED` replacement, path reopen, descriptor sync, exec, and controller shutdown flush the relevant mapped bytes. `open`, `stat`, `fstatat`, `access`, and `faccessat` follow the final logical symlink through overlay state unless no-follow behavior is requested, while `lstat`, `readlink`, `readlinkat`, and `AT_SYMLINK_NOFOLLOW` retain final-link semantics. The macOS-specific `O_NOFOLLOW_ANY` and `O_SYMLINK` modes return `ENOTSUP` before an encrypted open is staged. `stat`, `lstat`, `fstat`, and `fstatat` report logical attributes and plaintext file length instead of encrypted-container attributes when an upper entry or explicit logical permission override is active. For an encrypted upper regular file, path and descriptor metadata expose the same stable encrypted-backing device and inode rather than the anonymous plaintext descriptor identity. Untouched lower entries retain native host attributes. Create mode applies the child process's current umask and effective identity, and successful encrypted synchronization refreshes logical access and modification timestamps. Intercepted opens and mutations use effective credentials. `access` and `faccessat` use real credentials unless `faccessat` receives `AT_EACCESS`; invalid access-mode bits return `EINVAL`. All valid requests evaluate logical mode bits. Path operations also require execute/search permission on ancestors, and create/delete/rename operations require write plus execute permission on the affected parent directories. `O_NOFOLLOW` skips only the final symlink's access check and cannot bypass permissions on a regular final entry; `O_TRUNC` requires logical write permission even when combined with `O_RDONLY`. This is the classic owner/group/other mode model, not ACL, capability, sticky-bit, or identity virtualization.

For encrypted upper files larger than 1 MiB, a cold open without `O_TRUNC` validates the encrypted header and returns a correctly sized sparse anonymous plaintext vnode without scanning the body, including `O_WRONLY` and `O_RDWR` opens. Small files and truncating opens remain eager. Scalar and vector reads materialize the requested range with stateless adaptive readahead: four times the request clamped to 16-256 KiB, but never less than the request itself. Native writes populate their completed plaintext range directly; ciphertext writeback reads only that range and performs a 4 KiB ciphertext-block read-modify-write for partial boundary blocks, preserving both untouched plaintext ranges and sparse extensions without first decrypting the complete file. `mmap` materializes the requested mapping range before delegating to the native pager. Successful read, mapping, and write ranges are cached in both the Broker and each applicable open registration. `aio_read` and `lio_listio` reads materialize their declared offset and length, and `sendfile` does the same when no header or trailer makes its file-data length ambiguous. `SEEK_DATA`, `SEEK_HOLE`, a read-only `fcopyfile` source, and ambiguous `sendfile` requests require full materialization because those kernel interfaces can observe the vnode without a subsequent intercepted read; `fcopyfile` into a managed local descriptor fails with `ENOTSUP` because it cannot report destination writes. Authentication failure in an untouched body block is therefore reported as `EIO` when that block is first materialized rather than during cold open. The v2 ciphertext format, 4 KiB authenticated blocks, shared-vnode writeback, and native mmap-after-materialization model are unchanged; unlike FUSE, page faults themselves do not call the Broker.

`chmod`, `fchmod`, and `fchmodat` require the effective UID to own a non-allowlisted logical entry or be UID 0, update only logical overlay metadata, and never change lower host permissions. Symlink creation records an upper COW link without changing the lower host; an absolute target that names a prepared path inside the private backing tree is translated back to its logical host path before storage, which keeps executable aliases usable. Content-mutating `F_SETSIZE` and `F_PUNCHHOLE` operations on tracked encrypted descriptors return `ENOTSUP` because they cannot currently report the affected plaintext range to the Broker. For non-allowlisted paths, ownership changes, hard links, `clonefile`, `copyfile`, `removefile`, `removefileat`, and `freopen` currently return `ENOTSUP` while the hook is active. Timestamp mutation (`utimes`, `lutimes`, `futimes`, `futimens`, and `utimensat`), file flags (`chflags` and `fchflags`), extended-attribute mutation (`setxattr`, `fsetxattr`, `removexattr`, and `fremovexattr`), and non-zero extended-rename flags also return `ENOTSUP` before touching the lower host. `freopen` is rejected before either the supplied stream or destination is touched. An allowlisted path or untracked descriptor resolved beneath `/dev` is checked before these fail-closed cases and delegates to native libc, so the kernel's permissions and errno are preserved without VFS staging or audit. `posix_spawn_file_actions_addopen` supports read-only overlay paths; any non-allowlisted write, create, truncate, or append intent returns `ENOTSUP` without staging COW state. Direct syscalls, extended-attribute reads, and `seekdir`/`telldir` on merged directories remain outside the current hook surface.

The hook uses a thread-local recursion guard so VFS backing operations can call native libc without recursively re-entering the logical view. The filesystem and process guards check the process-wide initialized flag before accessing Darwin thread-local state, every ordinary filesystem-runtime lookup uses the same gate, and virtual `getattrlistbulk` checks the filesystem guard before consulting its FTS thread-local state; this keeps pre-initialization calls out of TLV and lazy-runtime bootstrap on both supported macOS architectures. The dylib initializer alone uses a separate direct runtime-construction entry point. Any filesystem call made recursively on that thread delegates to native libc, except a request already classified as managed mapped memory, which returns `EAGAIN` if it cannot enter the guard. Process execution remains fail-closed with `EACCES` when its guard cannot be entered. A process-wide `pthread_atfork` read/write barrier prevents `fork` from snapshotting an active filesystem hook and reinitializes that barrier in the child. If `fork` is re-entered while the forking thread itself owns the barrier's read side, the prepare handler temporarily suspends only that reader, drains readers on all other threads, acquires the write side, and restores the suspended reader in both the parent and child before the interrupted hook resumes; this avoids an unsupported read-to-write upgrade without weakening the cross-thread barrier. Thread-local destruction also releases a reader abandoned by a thread that exits before ordinary guard cleanup. The child handler resets only the process-local mutexes for inherited control streams; the parent-owned record lock remains the cross-process ordering boundary if another thread was inside a control transaction at fork. While the prepare handler owns that barrier, filesystem hooks invoked by an earlier-registered parent or child atfork callback on the forking thread delegate directly to native libc until the parent unlocks the barrier or the child reinitializes it; the same managed mapped-memory exception fails closed. Process preparation reports the filesystem runtime's tracked logical current directory before falling back to native `getcwd` or `PWD`; this keeps descendant execution logical even when libc traversal temporarily entered a prepared physical directory or the caller cleared `PWD`. Replacing the recursion escape hatch safely requires a complete native backend for all overlay host I/O; the hook-only implementation is therefore a cooperative boundary rather than a complete namespace.

For encrypted local files, successfully reported data writes are merged into the Broker's short writeback window and update the affected ciphertext blocks without forcing them to stable storage. Intercepted `fsync`, successful `F_FULLFSYNC`/`F_BARRIERFSYNC`, `MS_SYNC`, mapping teardown or write removal, tracked final close, normal process exit, and the pre-exec path request durable synchronization. A clean durable request skips `sync_all`; after mutations, one durable sync for the shared ciphertext inode satisfies all of its handles. Final close sends any hook-side fallback ranges in the same Broker request instead of synchronizing twice. When a run ends, the parent controller stops accepting new local Broker connections, drains requests it already accepted, and performs one final flush that first collects each live handle and then durably synchronizes each changed ciphertext inode once. Pre-registered writable mapping ranges and a plaintext identity fallback let it recover changes from a child that exits without closing its descriptors. A host crash or termination of the controller can still lose updates that were never durably synchronized. Opens of one ciphertext inode observe completed mutations through the same plaintext vnode; Broker mutation tokens serialize ordinary writes and append reservations, while writable shared mappings join the same sync and durability boundary. Attribute refresh after synchronization updates the logical path only while it still resolves to the same backing device and inode. An open descriptor whose path was unlinked or replaced can therefore sync and cross exec without failing or modifying the replacement path.

## Executable Preparation

Injectable executables and shebang scripts can run from their original visible paths. When SIP flags, dyld restrictions, library validation, Hardened Runtime, or architecture selection prevent injection, the execution controller copies the selected Mach-O slice into its exact mirrored path below `<workdir>/fs`, applies required processing, and ad-hoc signs it.

Prepared executable copies persist across runs. Reuse first requires a matching device/inode/size/timestamp/mode source identity and target OS/architecture variant. The cache record also stores the prepared destination's device/inode/size/timestamp/mode identity: an unchanged destination identity reuses the file without rereading it, while a changed or previously unrecorded identity triggers a complete MD5 comparison with the recorded prepared-output MD5. A matching fallback MD5 refreshes the destination identity and reuses the file; a missing checksum, mismatched MD5, source or target mismatch, unreadable destination, or non-executable destination rebuilds through the existing temporary preparation, architecture selection, ad-hoc signing, and atomic publication flow. This preserves content validation after any observable destination mutation while avoiding a complete read of an unchanged large executable on every exec. Ad-hoc re-signing preserves source entitlements. Descendant `posix_spawn` and `execve` calls use the authenticated execution-preparation channel and fail closed when preparation fails. `execvp` PATH search skips existing candidates that are not regular executable files and continues to later components; when `PATH` is absent it uses the macOS `_PATH_DEFPATH` value `/usr/bin:/bin`. If no later candidate succeeds, it returns `EACCES` when at least one candidate was denied and `ENOENT` only when none existed. If native `execve` of the prepared `execvp` candidate returns `ENOEXEC`, the hook prepares `/bin/sh` and invokes it with the prepared candidate followed by the caller's remaining arguments, matching the shell-script fallback expected from `execvp`. The execution store rejects physical paths elsewhere in the private work directory. Paths beneath `<workdir>/fs` are accepted only through overlay state so a relocated executable can request a cached sibling without exposing arbitrary work-directory files. A prepared process may inspect its own cached executable and ancestors, while unrelated private backing paths remain denied. A shebang interpreter goes through the same path, with its optional argument and prepared script path inserted before caller arguments. An executable replaced by encrypted business COW data never falls back to the stale lower executable, but executing that encrypted upper image remains unsupported until the execution protocol can pass an already-decrypted executable descriptor rather than only a path.

## Key Migration

Normal startup never changes an existing key. Migration is explicit and interactive:

```bash
agora-sandbox migrate-key --workdir <WORKDIR>
```

The command reads the current and replacement keys as visible text, acquires the same `.fs.lock`, validates the old key, decrypts each encrypted business file into an anonymous descriptor, prepares and verifies replacement ciphertext, and persists `.rekey.json` before replacing any file. Controller-managed cached executable copies and whiteouts are not re-encrypted. Old ciphertext remains in per-file backups until `.key.json` commits the new key. Staging, journal/key publication, every replacement or restoration rename, backup cleanup, and journal removal sync the affected parent directories. Recovery detects backup entries with `symlink_metadata`, so a dangling backup symlink remains a recoverable namespace object rather than being mistaken for absence. Startup rolls back an old-key journal or completes cleanup for a committed new-key journal before opening the workspace. Workspace construction and migration have synchronous filesystem/crypto cores; the public async runner and migration APIs dispatch them to Tokio blocking workers. Migration stages return over a channel and the caller's progress callback runs on the async caller rather than the blocking worker. Progress is stage-based rather than byte-based. Identical keys are rejected, and the old key is rejected after a successful migration.

There is no `clean` command or compatibility migration. Persistent state is removed only by explicitly deleting `<workdir>/fs` outside normal sandbox startup while no sandbox holds `.fs.lock`; other configured or temporary work directories are not deleted implicitly.

## Audit And Trace

The callback receives unified network, process, and file events. Process and file events are audit-only; network events may allow, deny, or proxy a connection.

The CLI emits audit events as structured `audit` fields through the project JSON logger. `log.file` selects the unified logger destination and defaults to `<workdir>/runtime/logs/sandbox.log`; a relative value is resolved from the workdir. The unified file also receives NFS status and other sandbox lifecycle records, while child stdout and stderr remain inherited without Agora records after logger initialization. A newly created log file uses mode `0600`. Opening an existing file does not change its mode; ownership and later permission management remain the caller's responsibility.

The filesystem hook publishes `filesystem.open` before an intercepted non-allowlisted open and `filesystem.close` before an intercepted tracked close. `/dev` operations are deliberately absent from this stream. Events carry the logical path, structured access flags, current process identity, and trace chain. Each audit publication carries a random request ID. A disconnect removes the cached client connection; the client reconnects and retries the same encoded request once, while the controller coalesces an in-progress duplicate or replays a completed response for up to 120 seconds from a 4096-entry cache. The callback and event UUID are therefore created at most once for one logical publication even when the first response is lost. Each thread reuses a healthy authenticated audit connection for multiple framed events. The controller applies a short initial-frame timeout and a 30-second idle timeout before every later frame on an ordinary connection; the one authenticated inherited control stream begins with `ping` and remains available across idle periods and nested sandbox activation. If a process-exit filesystem operation occurs after Rust thread-local destruction, the client uses one uncached connection or the inherited fallback instead of panicking or dropping the event. An unavailable audit controller fails the intercepted operation instead of silently bypassing audit.

## Host Keychain Behavior

The runner does not install a native Keychain-denial policy, and no Keychain API is intercepted or virtualized. Security.framework and `security` clients in descendants use the current user's host Keychain directly. Reads, refreshes, updates, and deletes therefore have the same host-visible effects inside and outside the sandbox.

Filesystem credential locations remain independent COW paths. For example, a CLI may combine configuration below the home directory, files below `~/Library/Application Support`, and a Keychain item. Externally removing one physical upper directory resets only that filesystem subtree and makes the next access fall through to its host lower path; it does not reset other credential directories or Keychain state.

Every run starts with one trace ID. Descendants append an ID and forward a bounded comma-separated chain, following `X-Forwarded-For` style. Process, file, and network events carry the same chain so one command can be correlated with its file and network activity.

## TLS Runtime Files

With TLS interception enabled, the runner reuses or creates the configured CA certificate and key, defaulting to `<workdir>/ca/ca.crt` and `<workdir>/ca/ca.key`. Each generated file is synchronized and atomically published from a same-directory temporary file. Before reusing the automatically managed default pair, the runner validates that the certificate and private key are well formed and match; a partial, malformed, or mismatched default pair is regenerated. A complete explicitly configured pair remains caller-owned and a validation failure is reported rather than overwritten. A CA-specific trust bundle is assembled below `<workdir>/ca` from the sandbox CA and native roots. File-based TLS clients receive that path; SecTrust clients receive the interception CA through internal hook configuration. There is no public independent trust-anchor option.

Leaf certificates are valid for one day and cached in memory for one hour. DNS names use public-suffix-aware wildcard selection, while IP addresses remain exact. The test suite covers copied `/bin/bash`, system `curl`, transparent CA trust, TLS interception, and a local HTTPS origin without an explicit `--cacert` argument.
