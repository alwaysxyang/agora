# Sandbox Filesystem And Executable Preparation

`agora-sandbox` provides a rootless, process-tree-scoped filesystem view on macOS. Supported path operations read through to the host filesystem, while sandbox mutations use a persistent copy-on-write tree. The original host paths are never modified except for roots deliberately listed in the compile-time native-passthrough allowlist; that list currently contains only `/dev` so device operations retain kernel semantics.

The filesystem and network views are cooperative boundaries, not a kernel namespace, and apply only to processes that load the Agora hook library. Executable preparation fails closed when a process cannot be made injectable. The runner does not install a native macOS process sandbox or virtualize Keychain APIs; descendants use the current user's host Keychain directly.

## Storage Layout

`SandboxConfig::new` defaults the work directory to `~/.agora-sandbox`. The CLI reads optional `workdir` from the `run` configuration and uses the same default when it is omitted; the SDK exposes `SandboxConfig::with_workdir`.

`<workdir>/fs` is the only persistent filesystem backing tree. Absolute logical paths are mirrored below it: `/usr/bin/curl` maps to `<workdir>/fs/usr/bin/curl`. There is no disk image, mount point, or separate `filesystem` directory.

Control data is stored in place:

```text
<workdir>/fs/
├── .fs.lock
├── .key.json              # encrypted mode only
├── .metadata              # managed-directory root marker
├── .vfs.lock
├── .rekey.json            # only while key migration is recoverable
├── usr/
│   └── bin/
│       └── .metadata
└── ...
```

Every physical upper directory, including merge-only directories, contains one valid `.metadata` marker. The marker chain from `<workdir>/fs/.metadata` to an upper object is continuous; an empty version-3 marker is valid and does not make the directory authoritative over lower. Hidden `.agora-write-lease-*` sidecars track writable encrypted entries. Hooked processes cannot access the physical work directory or any physical control path, even when they know the absolute path. Directory enumeration hides control entries. A sandbox may still create a logical business file with a reserved control name such as `.metadata`, `.fs.lock`, `.key.json`, `.vfs.lock`, or `.rekey.json`; exact names, dot-suffixed variants, and internal backing-name prefixes use an encoded physical filename and remain separate from control data.

Automatically managed TLS CA certificate, key, and trust-bundle files remain under `<workdir>/ca`. The CLI materializes its embedded, linker-signed hook before sandbox startup at `<workdir>/runtime/hook/<md5>/libagora_sandbox.dylib`, using `<workdir>/runtime/hook/.lock` to serialize publication. The lowercase MD5 covers the complete dylib and matching regular-file content is reused without rewriting it. A same-user regular file with the wrong size, unreadable content, or a mismatched checksum is atomically replaced from the embedded bytes; foreign-owned files remain an error. This controller-owned runtime cache is outside `<workdir>/fs`: it has no overlay metadata, filename or content encryption, lower-layer fallback, or filesystem audit representation. Prepared SIP-restricted executables are persistent plaintext cache entries at their mirrored paths below `<workdir>/fs`; for example, `/usr/bin/curl` is cached at `<workdir>/fs/usr/bin/curl`. They are controller-managed executable artifacts rather than encrypted business COW files and are reused while the recorded source identity matches.

## Storage Modes

`filesystem.local.encrypt: "plain"` in the CLI configuration selects the persistent `<workdir>/fs` tree without file-content encryption and rejects `filesystem.local.key`. Plain mode is the CLI and SDK default when the setting is omitted.

`filesystem.local.encrypt: "encrypted"` with a non-empty `filesystem.local.key`, or `SandboxConfig::with_encrypted_workspace`, selects encrypted mode. The first run creates `<workdir>/fs/.key.json` with a random salt and derived key identifier. Later runs derive the cipher again and reject a different key before starting the child. Existing unmanaged data is not imported into encrypted mode.

Encrypted regular files use content format version 2. Each container has two authenticated generation headers carrying a random file ID and logical length, followed by independently authenticated 4096-byte AES-256-GCM blocks. A per-file key is derived from the runtime cipher key and file ID with HKDF; each written block receives a fresh nonce and authenticates its file ID and block index. Absent or all-zero physical block slots represent sparse logical zeroes, so allocated block contents are authenticated but the sparse allocation map itself is not: removing or zeroing an entire slot can turn that block into a sparse zero. Content format version 1 is not supported, and encrypted deployments must start with a fresh `<workdir>/fs`.

The controller derives the runtime cipher key with PBKDF2-HMAC-SHA256 once per sandbox startup; injected descendants receive only the derived 32-byte key, so each exec does not repeat PBKDF2 or inherit the passphrase and salt as runtime configuration. Directory paths remain mirrored. For each encrypted business file or symlink, the original logical leaf bytes are authenticated-encrypted with AES-256-GCM under a filename-specific domain and encoded as an `enc_` URL-safe token. That ciphertext token is both the physical leaf name and the parent `.metadata` record key; there is no independently generated random alias, `backing_names` map, or separately persisted logical-name field. Filename encryption uses a fresh nonce, so recreating the same logical name may produce a different ciphertext token without introducing an unrelated backing name. Plain-mode entries and controller-managed executable caches retain literal logical names, with reserved prefixes escaped losslessly. Physical business files beneath `<workdir>/fs` remain ciphertext while the sandbox is running. Lower files without an authoritative upper entry are opened directly from their host paths.

Encrypted upper opens decrypt into anonymous, unlinked plaintext descriptors. A separate authenticated local-filesystem Broker in the parent retains a duplicate plaintext descriptor and the open ciphertext container; it is independent of the NFS Broker and is started only for encrypted mode. Successful intercepted `write`, `pwrite`, `writev`, and `pwritev` calls report their affected byte ranges immediately, and the Broker updates only the intersecting ciphertext blocks and logical length. This keeps long-open files current without waiting for close. Existing containers retain their physical inode during block updates and truncation, while namespace creation still uses the overlay's atomic publication flow. Direct host reads of upper storage therefore see only ciphertext, while the hooked process sees ordinary plaintext descriptors.

The root `.fs.lock` prevents two sandbox runs or a key migration from using the same work directory concurrently. `.vfs.lock` serializes short overlay metadata and publication transactions inside one process tree. A fork-aware per-process pool reuses unlocked descriptors for sequential transactions, opens distinct descriptors for overlapping transactions so advisory locking still serializes threads, and discards inherited pooled descriptors after a PID change. The same file stores an eight-byte metadata publication generation. Per-process metadata caches compare that generation while holding the VFS lock, including cached absence, so a publication by another descendant invalidates stale directory state without reopening every `.metadata` file. Cached directories also retain the physical marker identity; a marker removed or replaced outside the sandbox invalidates the local cache and advances the shared generation. Batched record lookup deduplicates the requested ancestor closure and reconciles each reachable path once. When an ancestor has no reachable upper directory and marker, deeper upper records are untrusted and skipped; an encountered whiteout still rejects requested descendants. Validation remains lazy and startup does not recursively scan the upper tree. A writable encrypted snapshot holds a shared lease on its backing identity, and the lease records the ciphertext destination currently attached to that identity. Writers do not block one another. Regular-file rename moves and retargets the source lease so its open snapshots continue writing to the renamed path; snapshots of a replaced target become detached. Unlink removes the current lease sidecar and detaches existing snapshots, whose later writeback is ignored instead of recreating the name. Directory rename still takes non-blocking exclusive leases for affected subtrees and returns `EBUSY` while an affected writable snapshot remains attached. Different work directories are independent.

## Copy-On-Write View

The VFS owns path normalization, physical-name encoding, lower-layer reads, whole-file copy-up, whiteouts, per-directory metadata, encryption, atomic publication, and logical owner/group/other authorization. Each authorized VFS operation resolves paths, checks the operation-specific permissions, and stages or applies its namespace change through one scoped overlay transaction and one `.vfs.lock` snapshot. Within that transaction, final-follow operations reuse the resolved logical endpoint for attribute checks, and ancestor search returns the immediate parent's effective attributes for a later parent write check; neither endpoint nor parent is resolved a second time. The hook is an adapter for libc operations, credential selection, descriptor tracking, and audit events; it does not calculate overlay or mode-bit policy or pre-authorize a later VFS mutation. Open remains two-phase: authorization and staging share the first transaction, native descriptor construction occurs without the namespace lock, and a short second transaction publishes `cow` only after descriptor construction succeeds.

Reads prefer an authoritative `cow` upper entry and reject a `whiteout`. Otherwise a lower file or directory is opened directly from its host path without copying it, creating upper directories or metadata, or passing it through decryption. Read-only regular opens and stat-family calls use the native host operation directly when the requested path, its resolved symlink target, and their ancestor chains have no overlay entry-state override. A logical-attribute override on the endpoint still requires full VFS metadata patching; an allowed ancestor attribute override does not disable the native metadata fast path after its execute/search permission has been checked, while a denied ancestor does. Mutating and special-flag operations continue through the full VFS path. A `cached` entry is non-authoritative and is reserved for explicit materialization such as executable preparation or a staged mutation; normal reads continue to use lower until the mutation commits as `cow`. A later staged write refreshes stale cached data when the lower checksum changes. Source-derived cached attributes refresh with that lower snapshot, while an explicit logical attribute override remains authoritative across copy-up and a failed native open. Cached lower MD5 values used by ordinary copy materialization are change detectors, not security primitives; executable caches use the recorded source identity without hashing the whole executable.

A successful write-intent open changes an entry to `cow`. Existing lower data is copied up first; newly created data exists only in the upper tree. An encrypted `O_CREAT|O_EXCL` open reserves the logical leaf's encrypted ciphertext token while holding `.vfs.lock`, so another VFS cannot create the same logical path before the first open commits; abandoning the staged open removes the reservation. Permission failures are rejected before copy-up; a later native open failure leaves any staged cache entry non-authoritative. COW entries are never refreshed from the lower path.

Before using upper state, the VFS reconciles it while holding `.vfs.lock`. A `cow` or `cached` record whose physical backing object was removed outside the sandbox is deleted together with its logical attributes, encrypted-name reservation, and attached write lease, after which lookup falls through to lower. A `whiteout` remains authoritative when no backing object exists; an unexpected object at a whiteout path is removed without clearing the whiteout. An attribute-only lower override remains valid without upper data. An unrecorded upper file or symlink is removed, and a physical directory without its own marker is removed recursively even when a descendant marker looks valid. Removing a whole upper directory outside the sandbox therefore makes the next access use lower in the same running process. Cleanup failure aborts the operation instead of exposing a partially reconciled view, while invalid JSON in an otherwise continuous marker chain remains a hard error.

Deletion records a `whiteout`, hiding any lower entry with the same logical path. Rename validates POSIX type, descendant, non-empty-directory, and materializable-file constraints before copy-up, preserves ordinary symlinks when materializing a lower directory, and then moves only upper state. Special files that would require copy-up fail without leaving staged upper data. Before VFS lookup, the hook normalizes logical absolute paths and checks the compile-time `NATIVE_PASSTHROUGH_ROOTS` list. `/dev` and its descendants currently bypass COW lookup, metadata overrides, backing-path rewriting, encryption, descriptor/directory tracking, and filesystem audit for every covered path- or descriptor-based filesystem operation; component matching excludes `/developer`, and normalization prevents `/dev/..` escapes. Relative `*at` paths are classified only after resolving their directory descriptor. Native kernel permissions and errors are authoritative on that branch, and write opens such as `/dev/null` never create COW metadata. Operations with two filesystem operands delegate to native libc only when both operands resolve inside the allowlist; a rename crossing the allowlist boundary fails with `EXDEV`, while unsupported link/clone/copy families retain `ENOTSUP`, so an allowlisted operand cannot expose another host path. Intercepted non-allowlisted `opendir`/`fdopendir` plus `readdir`/`readdir_r` enumeration merges NFS, upper, and lower names when an NFS route applies, otherwise upper and lower names only. It prefers NFS over upper and upper over lower, filters overlay whiteouts from the overlay portion, decrypts encrypted logical names, and hides controls. During managed macOS FTS traversal, interposed `getattrlistbulk` synthesizes that same merged view so system tools receive NFS and upper-only files as well as lower entries; `fts_children` and `fts_read` additionally filter whiteouts, repair synthetic metadata where libc reports `FTS_NS`, patch encrypted-file stat records with plaintext sizes and logical attributes, and present logical paths and names instead of backing paths. `rewinddir` rewinds every contributing stream and resets merged-view deduplication. `fdopendir` retains the descriptor's actual layer when the view changes after `open`; it opens any complementary layers before transferring descriptor ownership, so preparation failure leaves the caller's descriptor open.

Each directory's `.metadata` is versioned JSON. Version 3 has one `entries` record map; each record may contain entry state and logical attributes. For encrypted business files and symlinks, the authenticated filename ciphertext is the record key and the physical leaf name, so neither plaintext logical names nor `backing_names` or `name` fields are persisted. Plain-mode entries and controller-managed cached executables use literal UTF-8 record keys; non-UTF-8 bytes and names beginning with reserved `base64:` or `enc_` prefixes use `base64:<URL_SAFE_NO_PAD>`. The decoder can still read versions 1 and 2 when directly encountered, but normal startup neither recursively scans nor rewrites legacy metadata and compatibility is not guaranteed; deployments must start this format with a fresh `<workdir>/fs`. Entries are `cached`, `cow`, or `whiteout`; non-authoritative cached entries carry a materializer type and source identity, while ordinary copy materialization additionally carries a lower MD5. Logical mode, owner, group, and access/modification times are stored in the same record and remain separate from physical ciphertext attributes. Metadata and ciphertext publication first creates and syncs any missing ancestor markers, then syncs the temporary file, atomically renames it while holding `.vfs.lock`, and syncs the parent directory before returning success. A successful metadata publication advances the generation stored in `.vfs.lock` before releasing that lock.

## NFS Roots

The source module named `nfs` owns protocol-backed filesystem roots; the name describes Agora's generic network-filesystem layer and does not require the NFS wire protocol. `nfs/backend/mod.rs` defines the protocol-neutral backend trait and error boundary, while protocol-specific implementations live in private child modules. SMB2/3 is the first implementation and lives in `nfs/backend/smb/`; its storage type, sessions, path mapping, and protocol error adaptation are not visible outside that module. The existing `SmbRemoteConfig` public API is defined there and re-exported through `nfs` and `runner` without exposing the implementation module. The generic Broker and controller depend only on the storage trait. Later protocols must implement the same storage boundary instead of adding protocol logic to the hook or leaking implementation types into the generic NFS layer.

The CLI reads remote roots from the unified run configuration's `filesystem.nfs` array. An SMB
entry has `type: "smb"`, a logical `dir`, a `server` URI, and optional `username` and `password`.
The URI grammar is `smb://host[:port]/share[/remote/path]`; credentials in the URI, query strings,
and fragments are rejected. The SDK equivalent remains `SandboxConfig::with_smb_remote`, whose
typed configuration also supports an SMB domain. Logical roots must be normalized absolute
non-root paths and may not overlap another NFS root, `/dev`, or any part of `<workdir>`; validation
also compares existing canonical ancestors so a symlink alias cannot bypass those boundaries.

```json
{
  "tls": "off",
  "filesystem": {
    "local": { "encrypt": "plain" },
    "nfs": [
      {
        "type": "smb",
        "dir": "/network/team",
        "server": "smb://files.example.com/documents/projects/current",
        "username": "alice",
        "password": "secret"
      }
    ]
  }
}
```

An NFS root contributes the highest-priority namespace layer, so lookup order is `NFS > upper > lower`. An existing NFS entry wins over an upper entry, overlay whiteout, or lower entry with the same logical name. An NFS `ENOENT` falls through to the normal overlay lookup; any other NFS error fails the operation instead of silently exposing another layer. Directory enumeration merges all available layers and emits each logical name once with the same priority. Each configured root is also injected as a synthetic directory entry into its existing logical parent for both ordinary and managed FTS enumeration, without creating a host or upper placeholder; it hides a same-named local entry and remains visible while its backend is unavailable, while access still reports the backend error. Removing an NFS entry therefore reveals an existing upper/lower entry immediately, while removing a path absent from NFS applies normal overlay deletion. Existing fallback entries retain normal COW and encryption behavior. A create under an NFS route uses an existing visible upper/lower entry when one exists, but a path absent from every layer is created directly in NFS.

Remote objects themselves bypass COW storage, filename/content encryption, whiteouts, and `.metadata`. The runner does not mount the share in the host namespace. Instead, a per-run parent-process Broker owns credentials and one backend session holder per configured root. After the Broker is ready, its controller starts one independent connection probe per root without awaiting those probes before spawning the child. A successful probe retains the established backend session; a failed probe leaves the holder uninitialized so a later filesystem access retries normally. Each completed probe becomes a controller status event, and the runner writes one sanitized connected or unavailable line to stdout containing the logical root and endpoint but no username or password. Probe failure neither terminates the Broker nor the child. Every `filesystem.nfs` array entry receives a stable route index, so one run can expose multiple independent SMB roots. The injected hook receives only normalized logical routes plus a short-lived authenticated Unix socket; endpoint, share, username, domain, and password never enter the child configuration. The socket, opaque empty metadata anchors, and unlinked staging files live in a mode-protected short temporary directory under `/tmp` and are removed with the run. Named anchors contain neither a remote name nor file content. Stat and list responses create fresh anchors rather than caching one per remote path; the hook owns each claimed anchor through a short RAII lifetime, and unclaimed response resources expire from the Broker cache. NFS opens and closes still use the normal filesystem audit channel.

A regular-file open downloads one whole-file snapshot and returns an anonymous, unlinked local descriptor. Ordinary `read`, `write`, `pread`, `pwrite`, `lseek`, and `mmap` then operate on that descriptor without protocol-specific data hooks. A successful new or truncating open publishes its initial state immediately. Changed data replaces the whole remote file on intercepted `fsync`, full-sync `fcntl`, pre-exec flush, or last tracked close. Path `stat` and a later open in the same process first publish a writable snapshot for that path. An MD5 of the local snapshot avoids rewriting an unchanged file; MD5 is only a local change detector. The Broker serializes mutations per configured root. The SMB backend reads content and its baseline identity through one locked remote handle; writeback opens one locked handle, verifies that same handle's identity, writes, truncates, flushes, and obtains the resulting identity before releasing it. A mismatch returns `ESTALE` rather than overwriting a concurrent remote change. SMB rename uses replace-if-exists semantics. Rename detaches snapshots of a replaced destination before retargeting open source descendants. Unlink detaches matching open snapshots, and later sync or close succeeds without a path stat or recreating the removed path. A failed pre-registration open sends `abort` rather than publishing staged create/truncate state.

Selected NFS directories use synthetic logical views backed by opaque empty anchors for `stat`, `opendir`/`fdopendir`, `readdir`, relative `*at` operations, current-directory operations, and managed FTS traversal; overlay directory streams are attached to that view when fallback layers also exist. A successful remote `chdir` keeps the native process cwd on its opaque anchor and tracks the logical NFS path. Intercepted `posix_spawn` and `exec` calls replace any caller-provided remote-cwd variable with that tracked path. A new hook runtime restores it only when the inherited native cwd is a valid anchor beneath the configured Broker runtime and the logical path still belongs to a configured route, so external commands launched after `cd` retain the same logical directory without exposing the runtime path. `mkdir` creates in NFS only when the name is absent from every layer. Unlink/rmdir removes the selected NFS object first and otherwise delegates to overlay deletion. A rename whose source is selected from NFS is sent to the backend; a source selected from upper/lower remains an overlay rename when both operands stay in the same NFS route and no NFS destination shadows it. A rename crossing NFS roots or crossing between an NFS route and host/COW paths returns `EXDEV`; the configured root itself cannot be removed or renamed. Regular NFS files are presented as non-executable mode `0666`, directories as `0777`, and owner/group as the effective process identity; regular-file `X_OK` fails. Symlink, hard-link, ownership, mode, timestamp, flags, xattr, clone, and copy mutations are not currently represented by the backend trait and return `ENOTSUP` for a selected NFS object rather than mutating a same-named fallback object.

This is whole-file snapshot coherence, not a kernel shared-inode implementation. Two changed snapshots of the same baseline conflict after the first publication; unchanged snapshots never overwrite newer remote data. Every request carries a random request ID. The hook retries an ambiguous transport failure with the same ID, while the Broker executes the operation once, waits for an in-progress duplicate, or replays the completed response. Resource-bearing open, stat, and list responses require a follow-up claim; unclaimed handles and anchors are reclaimed when the bounded response cache expires. Close and abort retain bounded tombstones so retrying either operation is idempotent. A background connection-probe failure is informational; a backend/network failure during a covered filesystem operation fails that operation, and a Broker service failure terminates the run. Hook-side Broker reads and writes time out after 30 seconds; the Broker bounds an incomplete initial request to one second and a blocked response to five seconds, while transport writes suppress `SIGPIPE`. Unsynchronized changes can still be lost on fatal termination, and sharing an inherited NFS descriptor between processes that continue after a non-exec `fork` is outside the current supported coherence model. Large files require whole-file download, local staging space, and whole-file upload.

## Hook Semantics

The macOS hook is grouped by ownership domain. `hook/mod.rs` owns the dylib initializer, global initialized state, config/filesystem startup, filesystem exit-flush registration, and the generic errno setter shared by child domains. `hook/filesystem/mod.rs` owns the filesystem facade, shared runtime, guards, path/audit adaptation, descriptor identity, and preparation flows reused across libc operation families; its operation modules and C variadic shim are colocated under `hook/filesystem/`. `open.rs`, `descriptor.rs`, `metadata.rs`, `namespace.rs`, and `unsupported.rs` own the original operation families; `data.rs`, `mapping.rs`, and `lifecycle.rs` own plaintext data-write reporting, mapped-memory lifecycle, and fork retention. `nfs.rs` adapts logical NFS roots to the authenticated remote Broker without containing backend protocol logic. Directory enumeration and current-directory operations live in `hook/filesystem/directory/mod.rs`; Darwin FTS and virtual `getattrlistbulk` support live in its nested `fts.rs`. Parent-side encrypted content synchronization lives under `filesystem/broker`, independently of the generic remote backend and Broker under `nfs`; both use the crate-private descriptor-capable framing in `ipc`. `hook/network/mod.rs` owns `connect`/`connectx` interception and network recursion/runtime state, with raw socket conversion in `hook/network/socket.rs` and Security.framework trust interception in `hook/network/trust/mod.rs`. Process execution interception and its tests live under `hook/process/`. Narrow implementation dependencies are limited to native cleanup, logical stat patching for FTS, and the shared runtime's native `/dev` namespace helpers; operation policy remains in the VFS, local encrypted Broker, or NFS Broker.

The hook covers `open`, `openat`, `creat`, `fopen`, `stat`, `lstat`, `fstat`, `fstatat`, `access`, `faccessat`, `readlink`, `readlinkat`, `realpath`, `symlink`, `symlinkat`, truncate, deletion, ordinary rename, zero-flag `renamex_np`/`renameatx_np`, directory creation, current-directory operations, `opendir`/`fdopendir`/`readdir`/`readdir_r`/`rewinddir` enumeration, macOS `fts_open`/`fts_children`/`fts_read`/`fts_close` traversal and its `getattrlistbulk` enumeration, `write`/`pwrite`/`writev`/`pwritev` including Darwin non-cancel variants, `mmap`/`msync`/`munmap`/`mprotect`, `fork`, `close`, `fclose`, `fsync`, `dup`, `dup2`, and relevant `fcntl` operations. Relative `*at` operations resolve tracked directory descriptors through logical paths, including duplicated descriptors; successful close removes directory tracking immediately, while encrypted file state remains tracked until its last descriptor and mapping reference is gone. `realpath` resolves visible upper and lower components and symlinks but returns only the canonical logical path; both caller-provided buffers and libc-allocated null-buffer form are supported. Directory creation checks searchability and an already-visible endpoint before parent mutation permissions, so BSD `mkdir -p` receives `EEXIST` for an existing prefix. `fchdir` resolves the descriptor's logical path before changing the native current directory and fails closed when that resolution is unavailable. Successful local `chdir` and `fchdir` calls resynchronize the tracked path from the native current directory, translating a prepared upper directory back to its logical path and collapsing host aliases such as `/tmp` and `/private/tmp`; remote directory changes retain the logical NFS path and propagate it through the protected child runtime environment described above. Managed FTS streams force `FTS_NOCHDIR`, map prepared upper roots to logical presentation paths, and therefore do not perform per-entry current-directory resynchronization; untracked native FTS streams retain the defensive resynchronization path.

Encrypted upper regular-file descriptors refer to anonymous plaintext files opened with the caller's requested read/write mode; direct lower reads retain native host descriptors. Anonymous plaintext descriptors and their duplicates are always close-on-exec, and `F_SETFD` cannot clear that bit. Descriptor duplicates and writable `MAP_SHARED` mappings share one local Broker handle. Closing the last descriptor does not release that handle while a mapping remains, and a fork retains inherited local Broker handles in the child. `MAP_PRIVATE` mappings are never written back. Writable shared mappings register their complete file ranges before they can be modified; `msync`, `munmap`, removal of write permission, `MAP_FIXED` replacement, path reopen, descriptor sync, exec, and controller shutdown flush the relevant mapped bytes. `open`, `stat`, `fstatat`, `access`, and `faccessat` follow the final logical symlink through overlay state unless no-follow behavior is requested, while `lstat`, `readlink`, `readlinkat`, and `AT_SYMLINK_NOFOLLOW` retain final-link semantics. The macOS-specific `O_NOFOLLOW_ANY` and `O_SYMLINK` modes return `ENOTSUP` before an encrypted open is staged. `stat`, `lstat`, `fstat`, and `fstatat` report logical attributes and plaintext file length instead of encrypted-container attributes when an upper entry or explicit logical permission override is active. Untouched lower entries retain native host attributes. Create mode applies the child process's current umask and effective identity, and successful encrypted synchronization refreshes logical access and modification timestamps. Intercepted opens and mutations use effective credentials. `access` and `faccessat` use real credentials unless `faccessat` receives `AT_EACCESS`; invalid access-mode bits return `EINVAL`. All valid requests evaluate logical mode bits. Path operations also require execute/search permission on ancestors, and create/delete/rename operations require write plus execute permission on the affected parent directories. `O_NOFOLLOW` skips only the final symlink's access check and cannot bypass permissions on a regular final entry; `O_TRUNC` requires logical write permission even when combined with `O_RDONLY`. This is the classic owner/group/other mode model, not ACL, capability, sticky-bit, or identity virtualization.

`chmod`, `fchmod`, and `fchmodat` require the effective UID to own a non-allowlisted logical entry or be UID 0, update only logical overlay metadata, and never change lower host permissions. Symlink creation records an upper COW link without changing the lower host; an absolute target that names a prepared path inside the private backing tree is translated back to its logical host path before storage, which keeps executable aliases usable. For non-allowlisted paths, ownership changes, hard links, `clonefile`, `copyfile`, and `freopen` currently return `ENOTSUP` while the hook is active. Timestamp mutation (`utimes`, `lutimes`, `futimes`, `futimens`, and `utimensat`), file flags (`chflags` and `fchflags`), extended-attribute mutation (`setxattr`, `fsetxattr`, `removexattr`, and `fremovexattr`), and non-zero extended-rename flags also return `ENOTSUP` before touching the lower host. `freopen` is rejected before either the supplied stream or destination is touched. An allowlisted path or untracked descriptor resolved beneath `/dev` is checked before these fail-closed cases and delegates to native libc, so the kernel's permissions and errno are preserved without VFS staging or audit. `posix_spawn_file_actions_addopen` supports read-only overlay paths; any non-allowlisted write, create, truncate, or append intent returns `ENOTSUP` without staging COW state. Direct syscalls, extended-attribute reads, and `seekdir`/`telldir` on merged directories remain outside the current hook surface.

The hook uses a thread-local recursion guard so VFS backing operations can call native libc without recursively re-entering the logical view. Any filesystem call made recursively on that thread delegates to native libc. A process-wide `pthread_atfork` read/write barrier prevents `fork` from snapshotting an active filesystem hook and reinitializes that barrier in the child. Process preparation reports the filesystem runtime's tracked logical current directory before falling back to native `getcwd` or `PWD`; this keeps descendant execution logical even when libc traversal temporarily entered a prepared physical directory or the caller cleared `PWD`. Replacing the recursion escape hatch safely requires a complete native backend for all overlay host I/O; the hook-only implementation is therefore a cooperative boundary rather than a complete namespace.

For encrypted local files, every successfully reported data write updates the affected ciphertext blocks without forcing them to stable storage. Intercepted `fsync`, successful `F_FULLFSYNC`/`F_BARRIERFSYNC`, `MS_SYNC`, mapping teardown or write removal, tracked final close, normal process exit, and the pre-exec path request durable synchronization. The parent controller also performs a final durable Broker flush when the run ends; pre-registered writable mapping ranges and a plaintext identity fallback let it recover changes from a child that exits without closing its descriptors. A host crash or termination of the controller can still lose updates that were never durably synchronized. Multiple open plaintext snapshots of one ciphertext inode receive each synchronized range so sequential writes remain coherent; overlapping writes that complete concurrently across independent snapshots are ordered by Broker synchronization rather than providing kernel shared-inode atomicity.

## Executable Preparation

Injectable executables and shebang scripts can run from their original visible paths. When SIP flags, dyld restrictions, library validation, Hardened Runtime, or architecture selection prevent injection, the execution controller copies the selected Mach-O slice into its exact mirrored path below `<workdir>/fs`, applies required processing, and ad-hoc signs it.

Prepared executable copies persist across runs. An unchanged device/inode/size/timestamp/mode identity reuses the cached copy without hashing the whole source file. An executable cache record without a matching source identity is rebuilt. Ad-hoc re-signing preserves source entitlements. Descendant `posix_spawn` and `execve` calls use the authenticated execution-preparation channel and fail closed when preparation fails. The execution store rejects physical paths elsewhere in the private work directory. Paths beneath `<workdir>/fs` are accepted only through overlay state so a relocated executable can request a cached sibling without exposing arbitrary work-directory files. A prepared process may inspect its own cached executable and ancestors, while unrelated private backing paths remain denied. A shebang interpreter goes through the same path, with its optional argument and prepared script path inserted before caller arguments. An executable replaced by encrypted business COW data never falls back to the stale lower executable, but executing that encrypted upper image remains unsupported until the execution protocol can pass an already-decrypted executable descriptor rather than only a path.

## Key Migration

Normal startup never changes an existing key. Migration is explicit and interactive:

```bash
agora-sandbox migrate-key --workdir <WORKDIR>
```

The command reads the current and replacement keys as visible text, acquires the same `.fs.lock`, validates the old key, decrypts each encrypted business file into an anonymous descriptor, prepares and verifies replacement ciphertext, and persists `.rekey.json` before replacing any file. Controller-managed cached executable copies and whiteouts are not re-encrypted. Old ciphertext remains in per-file backups until `.key.json` commits the new key. Startup rolls back an old-key journal or completes cleanup for a committed new-key journal before opening the workspace. Workspace construction and migration have synchronous filesystem/crypto cores; the public async runner and migration APIs dispatch them to Tokio blocking workers. Migration stages return over a channel and the caller's progress callback runs on the async caller rather than the blocking worker. Progress is stage-based rather than byte-based. Identical keys are rejected, and the old key is rejected after a successful migration.

There is no `clean` command or compatibility migration. Persistent state is removed only by explicitly deleting `<workdir>/fs` outside normal sandbox startup while no sandbox holds `.fs.lock`; other configured or temporary work directories are not deleted implicitly.

## Audit And Trace

The callback receives unified network, process, and file events. Process and file events are audit-only; network events may allow, deny, or proxy a connection.

The filesystem hook publishes `filesystem.open` before an intercepted non-allowlisted open and `filesystem.close` before an intercepted tracked close. `/dev` operations are deliberately absent from this stream. Events carry the logical path, structured access flags, current process identity, and trace chain. Each thread reuses a healthy authenticated audit connection for multiple framed events; the controller accepts multiple frames per connection, and a disconnect removes the cached connection before a later operation reconnects. If a process-exit filesystem operation occurs after Rust thread-local destruction, the client uses one uncached connection instead of panicking or dropping the event. An unavailable audit controller fails the intercepted operation instead of silently bypassing audit.

## Host Keychain Behavior

The runner does not install a native Keychain-denial policy, and no Keychain API is intercepted or virtualized. Security.framework and `security` clients in descendants use the current user's host Keychain directly. Reads, refreshes, updates, and deletes therefore have the same host-visible effects inside and outside the sandbox.

Filesystem credential locations remain independent COW paths. For example, a CLI may combine configuration below the home directory, files below `~/Library/Application Support`, and a Keychain item. Externally removing one physical upper directory resets only that filesystem subtree and makes the next access fall through to its host lower path; it does not reset other credential directories or Keychain state.

Every run starts with one trace ID. Descendants append an ID and forward a bounded comma-separated chain, following `X-Forwarded-For` style. Process, file, and network events carry the same chain so one command can be correlated with its file and network activity.

## TLS Runtime Files

With TLS interception enabled, the runner reuses or creates the configured CA certificate and key, defaulting to `<workdir>/ca/ca.crt` and `<workdir>/ca/ca.key`. A CA-specific trust bundle is assembled below `<workdir>/ca` from the sandbox CA and native roots. File-based TLS clients receive that path; SecTrust clients receive the interception CA through internal hook configuration. There is no public independent trust-anchor option.

Leaf certificates are valid for one day and cached in memory for one hour. DNS names use public-suffix-aware wildcard selection, while IP addresses remain exact. The test suite covers copied `/bin/bash`, system `curl`, transparent CA trust, TLS interception, and a local HTTPS origin without an explicit `--cacert` argument.
